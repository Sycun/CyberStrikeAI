## Sink 驱动审计（Source → Sink）

**目的**：把"这个仓库有没有洞"变成一条可复核的追踪链，避免拿规则告警的数量当结论。

**顺序**

1. **列入口**：HTTP 路由与中间件、消息消费者、CLI/定时任务、反序列化点、模板渲染、文件上传、内部 RPC。
   每个入口记下它接受什么（body/query/header/文件名/序列化对象）以及是否有框架级校验。
2. **列 sink 类别**（只列这仓库真实存在的）：命令执行、SQL/NoSQL 拼接、文件路径与解压、外发请求（SSRF）、
   反序列化、模板求值（SSTI）、重定向、权限判定、密钥/凭据读取、日志注入到控制面。
3. **追数据流**：对每个 sink 反向找 source。写清三件事——入口在哪、中间经过哪些赋值/拼接/编解码、
   到 sink 时攻击者还能控制什么。"经过了某个函数"不等于"被过滤了"，要读到那行代码。
4. **判可达性**：配置开关、部署形态（是否启用该路由）、前置鉴权、类型约束，都可能让一条链断掉。
   断了就写"不可利用 + 断在哪"，不要为了凑数量保留。
5. **最小复现思路**：给到"什么样的输入、走哪条路径、触发哪个 sink"即可；不需要真实攻击载荷，
   也不要把 PoC 发往任何第三方目标。

**常见误判（逐条排除）**

- 把 ORM 的占位符执行当成字符串拼接；把模板自动转义当成"无转义"。
- 把只在校验通过的分支里出现的 sink 当成无条件可达。
- 把测试夹具/示例代码里的硬编码密钥当成生产泄露（要确认它是否被打进发布制品）。
- 把"能读到文件"直接写成"任意文件读取"——要确认路径分量是否真的可控、是否有前缀约束。

**供应链附加项**

- 锁文件与声明文件是否一致；依赖是否新增、改名（近似仿冒）、降级到含已知洞的版本。
- `postinstall`/构建脚本/自定义安装器会执行什么。
- 制品版本与源码版本是否同一提交；签名与校验和是否**真的被下游验证**，还是只是发布时生成了。

**交付形态**：每条发现 = 一句话结论 + 入口→sink 链路（文件:行）+ 判定依据 + 修复方向（收窄输入，而不是加一层黑名单了事）。
