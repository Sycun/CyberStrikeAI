## 输出边界判定（Who owns the trust break）

**目的**：把"能被注入"换成一条能落地的危害链——不可信内容要经过几个"仍被当数据"的假设，才最终变成动作。

**判据顺序**

1. **内容来源分级**：运维者控制的配置 / 已审核已安装的资产 / 用户当轮输入 / 第三方不可信内容
   （检索到的网页、上传文档、邮件工单正文、工具返回的外部数据）。
   注入要成立，必须至少有一条路径让后两类内容出现在"被当指令读"的位置。
2. **边界有没有在下游重新建立**：模型输出如果是 HTML、SQL 片段、URL、命令行、配置项，
   就要问下游是否**按数据消费**。只要它被再执行一次，注入面就从"话术"升级成"动作"。
3. **工具调用的授权点**：判断发生在服务端（策略/审批/HITL）还是仅写在工具描述里。
   只在提示里声明的约束不算防护——它是可被重写的内容。
4. **跨作用域读写**：检索库、记忆、项目事实是否按用户/会话分域。
   一条被投毒的检索条目能影响多少后续会话，决定它是单机问题还是横向问题。

**最小证据写法**：给出「注入内容进入点 → 被谁当指令读 → 触发哪个工具/输出消费 → 观察到什么副作用」，
四段缺一都不算成立。没有副作用的观察（复读提示、越狱语气）只记为信息面，不记为接管。

**修复方向的优先级**（从高到低）：在**服务端**为工具调用建授权与审批下限；收窄可调用面（不需要的工具不暴露）；
给不可信内容打标签并在拼进提示时与指令面隔离；下游按数据消费输出（转义、参数绑定、禁执行）。
不要写"加强系统提示词约束"作为主要缓解——那是同一层的自我承诺。
